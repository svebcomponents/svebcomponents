title: Build pipeline
description: Package Svelte custom elements for browsers, TypeScript, and server rendering.

`@svebcomponents/build` configures the Svelte compiler and tsdown. It runs
[attribute inference](/guides/attribute-inference/), writes browser bundles and
declarations, generates a custom elements manifest, and creates server output
when the package exports it.

Svelte compiles the component and generates the custom element class.
The build packages that output and guards Svelte's registration call so an
entrypoint can run more than once.

## Entrypoints from package exports

The CLI infers entrypoints from the `exports` field:

```json
{
  "exports": {
    ".": {
      "types": "./dist/client/FavoriteNumber.d.ts",
      "svelte": "./dist/client-svelte/FavoriteNumber.js",
      "default": "./dist/client/FavoriteNumber.js"
    }
  }
}
```

The CLI maps each browser export to a source file:

1. The export's `default` or `import` condition must start with
   `./dist/client/`.
2. The output path is mapped from `dist/client` to `src`.
3. A same-basename `.svelte` source is a svebcomponent.
4. A same-basename `.ts` or `.js` source receives a standard tsdown build.
5. Exactly one matching source must exist.
6. Subpath patterns (`"./*"`) are not inferred. Give each entry its own export
   key, or use [manual configuration](/guides/manual-configuration/).

In this example, `./dist/client/FavoriteNumber.js` resolves to
`src/FavoriteNumber.svelte`.

A `svelte` condition adds a second, lighter build, and a matching `/ssr` export
adds a server renderer. Both are covered in
[Publishing your package](/publishing/).

### Server preparation

An SSR-enabled component can acquire its own data on the server by adding an
adjacent `<entry>.ssr.ts` or `.js` module next to the component. The build
includes it in the server output and serializes its values for the client.

See the
[`SsrPrepare` signature](/packages/build/#server-preparation) and
[asynchronous components](/server-rendering/#asynchronous-components).

## Element types and manifest

The build describes each direct `.svelte` entry in two forms:

- `custom-elements.json` for editors and custom-element tooling
- TypeScript declarations for the element, tag, props, and events

```ts
import "my-components";

const el = document.querySelector("simple-component");
el?.count; // number | undefined
```

The analyzer reads props, `$host()` events, slots, CSS custom properties, and
component comments. See [Authoring components](/authoring/).

### Static tags only

The analyzer needs a literal tag in `<svelte:options>` and a direct `.svelte`
entry.

A dynamic tag or Svelte's bare `customElement` shorthand cannot appear in the
manifest or generated types. A component re-exported through a `.ts` entry is
also invisible to the analyzer. Export the `.svelte` file as the entrypoint.

## What ends up in the browser bundle

Apps load `dist/client` from a URL or a bundle that resolved its imports. The
browser builds inline each bare specifier, whatever `package.json` calls it. It
leaves Node builtins, relative and absolute paths, and protocol imports alone.
The build fails if it cannot resolve a specifier selected for inlining.

Declare dependencies that consumers must install. The browser build includes
their code. Declare the package whose types your element types name, or
`svelte` to
[register your Svelte template types](/publishing/#ship-the-svelte-template-types),
and the browser output carries its code either way.

List a dependency in `neverBundle` when the host must provide it:

```json
{
  "svebcomponents": { "neverBundle": ["@acme/design-system"] }
}
```

Entries match the whole specifier, so cover subpaths too if the package has
them. Server output keeps standard externalization. Node resolves declared
dependencies at runtime. See the
[`@svebcomponents/build` reference](/packages/build/#what-ends-up-in-the-browser-bundle).

## Manual configuration

When export inference cannot express your layout, a
[`svebcomponents.config.ts`](/guides/manual-configuration/) file replaces it
and exposes each build option.

For installation, the generated outputs and the full pipeline, see the
[`@svebcomponents/build` reference](/packages/build/).
