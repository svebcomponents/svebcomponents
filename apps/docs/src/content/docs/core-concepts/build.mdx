`@svebcomponents/build` provides the build pipeline around a Svelte custom
element package. It compiles Svelte for the browser, runs
`@svebcomponents/auto-options`, and emits TypeScript declarations alongside
the JavaScript output.

## Component Entrypoints

Each custom element needs an entrypoint that re-exports the Svelte component:

```ts
import Component from "./Component.svelte";

export default Component;
```

The component itself declares its tag:

```svelte
<svelte:options customElement="favorite-number" />
```

Consumers import the entrypoint for the side effect of defining
`<favorite-number>`. Svelte's generated `customElements.define()` call is made
idempotent at build time, so it no-ops if the component (or a bundle
containing it) is ever evaluated more than once.

For a tag that can't be a literal in `<svelte:options>` (e.g. computed at
build time), fall back to `@svebcomponents/utils`'s `defineElement` in the
entrypoint instead — the same guarded registration, called by hand:

```ts
import { defineElement } from "@svebcomponents/utils";

import Component from "./Component.svelte";

export default Component;
defineElement(tagName, Component);
```

## Zero-config Builds

For the common case, the CLI infers component entrypoints from the `exports`
field in `package.json`:

```json
{
  "exports": {
    ".": {
      "types": "./dist/client/index.d.ts",
      "svelte": "./dist/client-svelte/index.js",
      "default": "./dist/client/index.js"
    }
  }
}
```

The inference follows three rules:

1. The export's `default` or `import` condition must contain `dist/client`.
2. The output path is mapped from `dist/client` to `src`.
3. If that exact source file does not exist, the CLI looks for the same path
   with a `.ts` extension.

In this example, `./dist/client/index.js` resolves to `src/index.ts`.

## Svelte Conditional Exports

The standalone `default` build includes the Svelte runtime so it can work in
applications that do not use Svelte.

When the package is consumed by a Svelte application, bundling another copy
of the runtime is often unnecessary. Adding a `svelte` condition asks the CLI
to create a second build that leaves `svelte` and `svelte/*` imports external:

```json
{
  "exports": {
    ".": {
      "types": "./dist/client/index.d.ts",
      "svelte": "./dist/client-svelte/index.js",
      "default": "./dist/client/index.js"
    }
  }
}
```

Svelte-aware tooling such as SvelteKit and `@sveltejs/vite-plugin-svelte` can
select `dist/client-svelte/index.js` and share the host application's Svelte
runtime. Other consumers select the standalone `default` build.

:::caution
The Svelte-aware build relies on Svelte runtime internals. Those internals are
versioned with Svelte and its compiler, but they are not a semver-stable public
API: a patch or minor compiler release can change the runtime contract in ways
that break previously compiled output. Only use this optimization when the
component package and consuming application are built with the same Svelte
version. Keep the standalone `default` export as the safe fallback for other
consumers.
:::

Every matching export becomes a component entrypoint, so a package can expose
more than one custom element:

```json
{
  "exports": {
    ".": {
      "types": "./dist/client/index.d.ts",
      "svelte": "./dist/client-svelte/index.js",
      "default": "./dist/client/index.js"
    },
    "./button": {
      "types": "./dist/client/button.d.ts",
      "svelte": "./dist/client-svelte/button.js",
      "default": "./dist/client/button.js"
    }
  }
}
```

## Optional SSR Output

SSR is enabled per component by adding an export with the same key followed by
`/ssr`:

```json
{
  "exports": {
    "./button": {
      "types": "./dist/client/button.d.ts",
      "svelte": "./dist/client-svelte/button.js",
      "default": "./dist/client/button.js"
    },
    "./button/ssr": {
      "types": "./dist/server/button-ssr.d.ts",
      "svelte": "./dist/server-svelte/button-ssr.js",
      "default": "./dist/server/button-ssr.js"
    }
  }
}
```

The browser export defines the custom element. The matching SSR export
provides the renderer that a server application can register.

SSR is currently in beta. See [SSR](/core-concepts/ssr/) for its stability and
security considerations.

## Element Types & Manifest

Every build also writes two files describing the elements your package
declares:

- `custom-elements.json` — a
  [custom elements manifest](https://github.com/webcomponents/custom-elements-manifest)
  (schema 2.1.0). Editors read it directly for HTML completions, and the wider
  custom elements tooling ecosystem consumes it.
- `custom-elements.d.ts` — TypeScript declarations generated from the same
  analysis, so consuming templates know your tags and what they accept.

Publish both by listing them in `files`, and point tooling at the manifest:

```json
{
  "customElements": "custom-elements.json",
  "files": ["dist", "custom-elements.json", "custom-elements.d.ts"]
}
```

Consumers pick up the declarations by including the file once:

```ts
/// <reference types="my-components/custom-elements.d.ts" />
```

### What Gets Described

Props become attributes with the type and reflection settings
[auto-options](/core-concepts/auto-options/) inferred. Props typed with
TypeScript carry their declared type and JSDoc description; untyped props fall
back to the attribute converter's type, so a `Number` prop is still typed
`number`.

The declarations register your tag in `HTMLElementTagNameMap` — so
`document.querySelector("my-button")` returns the right element type — and
augment the template surfaces of Svelte (`SvelteHTMLElements`), Vue
(`GlobalComponents`) and React (`JSX.IntrinsicElements`). Augmenting a
framework you do not use is inert, so a Svelte-only consumer is unaffected by
the Vue and React blocks.

:::note
The React augmentation describes React 19 and later. Earlier versions
stringify every prop passed to a custom element and do not attach listeners
for custom event names.
:::

### Events

Events are collected from the pattern this project endorses:

```svelte
<script lang="ts">
  interface ChangeDetail {
    value: string;
  }

  const emit = (value: string) =>
    $host().dispatchEvent(new CustomEvent<ChangeDetail>("change", { detail: { value } }));
</script>
```

The explicit type argument is what makes `detail` typed — it is read verbatim,
with no type checker involved. Relying on inference from the `detail` value
instead still records the event, but its detail becomes `unknown`.

Callback props (`onPick`) are _not_ treated as events. They appear on the DOM
element interface, where `element.onPick = fn` genuinely works, but never on
the template surface: in a template `onPick={fn}` is event-handler syntax
rather than a property assignment, so listing it there would type-check a
handler that never runs.

### Slots & CSS Custom Properties

Statically named `<slot>` elements are collected automatically. CSS custom
properties are collected when the component _reads_ one it does not itself
define — those are the ones a consumer is expected to supply. A `var()`
fallback becomes the documented default.

Anything the scan cannot see can be documented on the component comment, which
also supplies descriptions:

```svelte
<!-- @component
A fancy button.

@slot - The button label.
@event change - Fired when the selection changes.
@cssprop --fancy-radius - Corner radius.
-->
```

Documentation is additive: it adds descriptions, or declares a member the scan
could not find. It never overrides inferred structure.

## Manual Configuration

Package exports are the recommended configuration for straightforward
packages. When you need different source paths or output directories, create
`svebcomponents.config.ts`:

```ts
import { defineConfig } from "@svebcomponents/build";

export default defineConfig({
  entry: "src/index.ts",
  outDir: "dist/client",
  svelteOutDir: "dist/client-svelte",
  ssr: true,
  ssrOutDir: "dist/server",
  ssrSvelteOutDir: "dist/server-svelte",
});
```

`svelteOutDir` enables the Svelte-aware browser build.
`ssrSvelteOutDir` does the same for the optional server renderer.

For installation, every configuration option, and the exact generated
outputs, see the [`@svebcomponents/build` reference](/packages/build/).
