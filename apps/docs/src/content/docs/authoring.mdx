title: Authoring components
description: Props, events, slots and styling in a Svelte component that ships as a custom element.
---

A svebcomponent is a Svelte 5 component whose props, events, slots, and CSS
custom properties form an HTML element API.

The build reads these declarations to produce the element's TypeScript types
and
[custom elements manifest](/guides/build/#element-types--manifest).

## Props

Declare props with `$props()` and type them. The type is what makes an
attribute arrive as something other than a string:

```svelte
<script lang="ts">
  interface Props {
    /** How many items to show at once. */
    pageSize: number;
    featured?: boolean;
  }

  let { pageSize, featured = false }: Props = $props();
</script>
```

Prop names stay camelCase in JavaScript; their attributes are kebab-cased:

| Prop             | Attribute         |
| ---------------- | ----------------- |
| `value`          | `value`           |
| `favoriteNumber` | `favorite-number` |
| `isFeatured`     | `is-featured`     |

`string`, `number`, `boolean`, arrays and object types are each mapped to the
matching Svelte attribute converter, and every prop reflects back to its
attribute by default. JSDoc comments on the prop become descriptions in the
manifest and the generated types.

See [how attribute inference works](/guides/attribute-inference/) for the full
list of recognised types and how to override any of them.

:::caution[Consumers on Svelte: pass expressions]
Svelte 5 assigns attribute values directly to JavaScript properties under
certain conditions, which bypasses the attribute converter. From a Svelte
template write `page-size={20}`, not `page-size="20"`.
See [sveltejs/svelte#12624](https://github.com/sveltejs/svelte/issues/12624).
:::

### Properties that are not attributes

An attribute can only ever be a string. A prop typed as a function, a snippet,
or another non-serialisable value is exposed as a property on the element and
left out of the attribute list entirely, because there is no string form for a
consumer to write in markup.

## Events

Dispatch events from the host element with
[`$host()`](https://svelte.dev/docs/svelte/$host). This is the pattern
svebcomponents endorses, and the only one it can describe:

```svelte
<script lang="ts">
  interface ChangeDetail {
    value: string;
  }

  const emit = (value: string) =>
    $host().dispatchEvent(
      new CustomEvent<ChangeDetail>("change", { detail: { value } }),
    );
</script>
```

The build reads the explicit `CustomEvent` type argument without running a type
checker. Without that argument, it records the event with `unknown` detail.

Each event joins a typed event map that narrows listeners:

```ts
el.addEventListener("change", (event) => event.detail.value);
```

:::note[Callback props are not events]
A prop like `onPick` appears on the element interface. The build omits it from
attributes because templates interpret `onPick={fn}` as event-handler syntax,
not a property assignment.
:::

`createEventDispatcher` still works, but its events are not forwarded through
the hydration host. See
[hydration limitations](/server-rendering/hydration/#limitations).

## Slots

The build collects named `<slot>` elements:

```svelte
<div class="card">
  <slot name="header"></slot>
  <slot></slot>
</div>
```

Consumers fill them with light DOM children, as with any web component:

```html
<my-card>
  <h2 slot="header">Title</h2>
  <p>Body</p>
</my-card>
```

:::caution[Slots disable hydration today]
A component that declares `<slot>` elements renders on the server and
re-renders on upgrade. Svelte 5 compiles slots without hydration support. See
[hydration limitations](/server-rendering/hydration/#slots).
:::

## Styling

Component styles are scoped by the shadow root, so nothing leaks in or out.
Style the element itself with `:host`, and give consumers explicit hooks rather
than expecting them to reach inside:

```svelte
<style>
  :host {
    display: inline-block;
    border-radius: var(--card-radius, 4px);
  }

  .title {
    color: var(--card-title-color, currentColor);
  }
</style>
```

The build adds CSS custom properties that the component reads but does not
define to the manifest. A `var()` fallback becomes the documented default.

For consumers who need to reach a specific inner node, add `part` attributes;
`::part()` works as it does on any custom element.

## Component comments

The component comment supplies descriptions, and can declare a member the build
could not find on its own:

```svelte
<!-- @component
A fancy button.

@slot - The button label.
@event change - Fired when the selection changes.
@cssprop --fancy-radius - Corner radius.
-->
```

Component comments add descriptions and members that the scan cannot find.
They do not override inferred structure.

## Declaring the tag

Every component declares its own tag with Svelte's string shorthand:

```svelte
<svelte:options customElement="favorite-number" />
```

Use the object form when you need `shadow` or a custom `extend`:

```svelte
<svelte:options customElement={{ tag: "favorite-number" }} />
```

:::caution[The tag must be a literal]
svebcomponents reads the tag from your source at build time to write the
manifest, the element types and the SSR renderer's self-registration. A
dynamically interpolated tag (`customElement="{x}"`) or the bare
`customElement` boolean shorthand cannot be read. auto-options warns and leaves
`<svelte:options>` untouched, which also means no inferred props and no
hydration. Use a plain string literal or the object form.
:::
