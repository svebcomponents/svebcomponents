:::caution[Beta]
SSR is in beta. Its APIs and generated output may change before 1.0. Svelte's
SSR serializer validates and escapes attribute names, attribute values, and tag
names; XSS regression tests cover those paths. The package has not had an
independent security audit. Your renderer must escape untrusted shadow-root
content passed through `{@html}`.
:::

Browsers instantiate custom elements from registered classes. A server renderer
sees an HTML tag without that class.

svebcomponents gives each custom element a server renderer based on Lit's
`ElementRenderer` model. It serializes the shadow root as declarative shadow
DOM.

## Package-author Flow

A component package exposes its browser entrypoint and a matching SSR
entrypoint:

```json
{
  "exports": {
    ".": {
      "types": "./dist/client/ExampleComponent.d.ts",
      "svelte": "./dist/client-svelte/ExampleComponent.js",
      "default": "./dist/client/ExampleComponent.js"
    },
    "./ssr": {
      "types": "./dist/server/ssr.d.ts",
      "svelte": "./dist/server-svelte/ssr.js",
      "default": "./dist/server/ssr.js"
    }
  }
}
```

The browser entrypoint defines the custom element. During the build, the SSR
entrypoint is generated as an `ElementRenderer` subclass that knows how to
render the Svelte component on the server.

The optional `svelte` conditions create renderer and browser builds that share
the consuming application's Svelte runtime, with the
[version-compatibility tradeoff](/publishing/#optional-a-lighter-build-for-svelte-consumers)
that carries.

See [Publishing your package](/publishing/#optional-server-renderable-output)
for how matching `/ssr` exports enable this output.

## App-author Flow

The consuming application needs two pieces of setup.

First, add the svebcomponents transform before the Svelte plugin:

```ts
import { sveltekit } from "@sveltejs/kit/vite";
import svebcomponents from "@svebcomponents/ssr/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [svebcomponents(), sveltekit()],
});
```

The plugin adds `@svebcomponents/ssr` to Vite's `ssr.noExternal`. If your
component package ships a raw `.svelte` export, add the package through the
plugin's `noExternal` option:

```ts
svebcomponents({ noExternal: ["my-component-package"] });
```

Load the component's server renderer once, for example from `hooks.server.ts`:

```ts
import "my-component-package/ssr";
```

The build reads the tag from `<svelte:options customElement>` and writes it into
the renderer. Importing that renderer registers it with
`ElementRendererRegistry`. The registry installs the DOM shim before the
renderer, regardless of import order or bundler chunks.

:::note
If the component's tag could not be read at build time (see
[static tags only](/guides/build/#static-tags-only)), the generated
renderer does not self-register, and the app registers it by hand:

```ts
import { ElementRendererRegistry } from "@svebcomponents/ssr";
import MyComponentRenderer from "my-component-package/ssr";

ElementRendererRegistry.set("my-component", MyComponentRenderer);
```

:::

## Other custom elements

The SSR pipeline accepts any custom element with a Lit `ElementRenderer`,
including Lit elements:

```ts
import { LitElementRenderer } from "@lit-labs/ssr/lib/lit-element-renderer.js";
import { ElementRendererRegistry } from "@svebcomponents/ssr";

ElementRendererRegistry.use(LitElementRenderer);
```

`use()` registers a renderer that selects elements through Lit's static
`matchesClass` hook. It covers each Lit element in the app. A registration made
with `ElementRendererRegistry.set()` takes precedence for its tag.

svebcomponents renderers implement `matchesClass`, so Lit's `render()` can use
them:

```ts
import { render } from "@lit-labs/ssr";
import MyComponentRenderer from "my-component-package/ssr";

render(html`<my-component title="Hello"></my-component>`, {
  elementRenderers: [MyComponentRenderer],
});
```

## Asynchronous components

Two component behaviors require an asynchronous host integration:

1. **The component awaits while rendering:** an `await` in its instance
   script, or anywhere Svelte's `experimental.async` allows one.
2. **Its preparation hook returns a promise:** the adjacent
   `<entry>.ssr.ts` module described in
   [server preparation](/guides/build/#server-preparation) module,
   whose default-exported `SsrPrepare` function may return a promise.

A hook that returns nothing keeps the synchronous path. This includes a hook
that exits because the host supplied the value it would have fetched.

### Preparation hooks

A preparation hook supports two server-specific needs:

- **Server-only dependencies stay off the client.** The build includes
  `<entry>.ssr.ts` in the server output. An `await` in the component includes
  its dependencies in both outputs.
- **The result survives hydration.** Properties set through the hook's
  `setProperty` join rich-property serialization, so the client adopts the
  prepared value instead of fetching it again. A value awaited inside the
  component is local state: it is not serialized, and the browser repeats the
  work.

Awaiting in the component is the right tool when the asynchrony is part of
rendering. The hook is the right tool when the component owns acquiring its
own data.

## Async Rendering Outside Svelte

Svelte gates asynchronous server rendering behind a module flag. A Svelte app
compiled with `compilerOptions.experimental.async` sets it.

A non-Svelte host must set the flag on the server. The component package cannot
set it because its server bundle and `@svebcomponents/ssr` use separate Svelte
runtime copies:

```ts
import "@svebcomponents/ssr/enable-async";
```

Without this import, `render()` uses synchronous mode and an async component
throws `await_invalid`. SvelteKit apps compiled with `experimental.async` do
not need the import.

## Render flow

On the server, the Vite plugin finds custom element tags in Svelte templates
and rewrites them to a wrapper component. The wrapper:

1. Looks up the custom element and its registered renderer.
2. Passes attributes and properties to that renderer.
3. Emits the rendered shadow root as declarative shadow DOM.

In the browser, the wrapper renders the custom element tag. The browser upgrades
it, and svebcomponents [hydrates](/server-rendering/hydration/) the
server-rendered shadow DOM in place.

The host integration changes by framework; the custom element does not. See
[Framework Integrations](/server-rendering/other-frameworks/).

For runtime APIs, direct package usage, transform details, and the complete
list of limitations, see the
[`@svebcomponents/ssr` reference](/packages/ssr/).
