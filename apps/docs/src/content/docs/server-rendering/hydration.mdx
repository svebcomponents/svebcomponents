---
title: Hydration
description: How server-rendered declarative shadow DOM is adopted instead of re-rendered when a Svelte-built custom element upgrades.
---

Svelte's generated custom elements mount from scratch when they upgrade. The
constructor attaches a shadow root, which clears the declarative shadow root
from the server. The browser then creates each node again.

Components built with `@svebcomponents/build` adopt the server-rendered shadow
DOM. Svelte keeps the nodes and styles, then connects its reactivity.

The build enables hydration for each SSR component. Set `hydratable: false` to
disable it.

## Hydration flow

svebcomponents uses Svelte's public extension points:

1. During the build, [auto-options](/guides/attribute-inference/) injects
   Svelte's official
   [`customElement.extend`](https://svelte.dev/docs/svelte/custom-elements#Component-options)
   option, wiring in a wrapper class from `@svebcomponents/ssr/hydration`.
2. The wrapper intercepts the `attachShadow` call in the generated element's
   constructor and claims the declarative shadow root before it would be
   cleared.
3. On connect, the wrapper hydrates the claimed shadow root with Svelte's
   public [`hydrate()`](https://svelte.dev/docs/svelte/imperative-component-api#hydrate)
   API instead of mounting.
4. The server and client render through the same internal `HydrationHost`
   component. The generated SSR entry uses a server build of that component;
   the client hydrates against it.
5. In a hydrating Svelte host such as SvelteKit, the server and browser wrappers
   render matching `<svelte:element>` fragments. Export conditions select each
   wrapper. The host claims the existing element before it can discard the
   shadow root.
6. The server serializes rich props into the shadow output. The wrapper restores
   them before hydration, even if the host supplies props after its own
   hydration finishes.

## Fallbacks

The wrapper uses Svelte's mount path in four cases:

| Situation                                                                   | Behaviour                                                |
| --------------------------------------------------------------------------- | -------------------------------------------------------- |
| No declarative shadow root (the element was never server-rendered)          | Plain client mount                                       |
| The component declares slots (see [below](#slots))                          | Plain client mount                                       |
| Re-connection after teardown (removed long enough for Svelte to destroy it) | Fresh mount                                              |
| Hydration mismatch                                                          | Svelte logs a warning, clears the shadow root, re-mounts |

Each fallback re-renders the component.

## Limitations

### Slots

Components that declare `<slot>` elements use the mount path and re-render on
upgrade. In dev mode, the element logs a `console.info` for this fallback.

Svelte 5 compiles `<slot>` elements in custom-element mode through a legacy
transform without hydration support. Svelte plans to remove that transform in
version 6.

### Legacy component events

`createEventDispatcher` events are not forwarded through the hydration host.
Events dispatched through [`$host()`](https://svelte.dev/docs/svelte/$host)
bubble from the custom element.

### Component exports

`export`ed component functions are not exposed as element methods on hydrated
hosts.

## Bundle cost

Hydration support adds about **4–5&nbsp;KB gzipped** to a self-contained
client bundle: Svelte's hydration internals plus the wrapper. Builds that share
the host application's Svelte runtime through the
[`svelte` condition](/publishing/#optional-a-lighter-build-for-svelte-consumers)
reduce that cost. Set `hydratable: false` for client-only components.

## Opting out

Disable hydration for a package in `svebcomponents.config.ts`:

```ts
import { defineConfig } from "@svebcomponents/build";

export default defineConfig({
  hydratable: false,
});
```

To control one component, declare `extend` in
`<svelte:options customElement={{ ... }}>`. Auto-options preserves your
extension. The component uses Svelte's mount behavior unless the extension
implements hydration.
